## 1. 质量门禁概述

### 1.1 Purpose

Quality 门禁 are checkpoints that must be passed before proceeding to the next phase. They ensure:
- 文档间的一致性
- 交付物的完整性
- 需求的可追溯性
- 无矛盾或遗漏

### 1.2 门禁结构

```
Phase 1: Requirements Gate
    ↓ (PRD complete, reviewed, approved)
Phase 2: Design Gate
    ↓ (Architecture, API, UI design complete)
Phase 3: Implementation Gate
    ↓ (Code complete, tests passing)
Phase 4: Testing Gate
    ↓ (All tests passed, defects resolved)
Phase 5: Release Gate
    ↓ (All gates passed, documentation complete)
Release
```

## 3. 文档规范

### 3.1 文档模板

**All documents must include:**

```markdown
# Document Title

> Version: X.Y
> Date: YYYY-MM-DD
> Status: [Draft/Review/Baselined/Superseded]
> Owner: [Name/Role]
> Related: [List of related documents]

---

## 1. Section Title

### 1.1 Subsection

Content here...
```

### 3.2 版本控制

**版本编号:**

| Type | Format | When to Use |
|------|--------|-------------|
| 主版本 | X.0 | 重大变更、新增章节 |
| 次版本 | X.Y | 新增内容、重大更新 |
| 补丁 | X.Y.Z | 小修、澄清 |

**版本历史表:**

```markdown
## Version History

| Version | Date | Author | Changes |
|---------|------|--------|---------|
| 1.0 | 2026-07-09 | Author | Initial version |
| 1.1 | 2026-07-10 | Author | Added section X |
| 1.1.1 | 2026-07-11 | Author | Fixed typo in Y |
```

### 3.3 状态定义

| Status | Meaning |
|--------|---------|
| Draft | Work in progress, not reviewed |
| Review | Under review, feedback requested |
| 已基线化 | 已评审、已批准、受变更控制 |
| Superseded | Replaced by newer version |

### 3.4 命名规范

**文件:**
```
{category}-{topic}-{version}.md

Examples:
architecture-system-architecture-v1.0.md
api-design-v1.0.md
ui-design-system-v1.0.md
test-strategy-v1.0.md
```

**章节:**
- Use numbered sections (1., 1.1, 1.1.1)
- Maximum 4 levels of nesting
- Use descriptive titles

### 3.5 交叉引用规范

**内部引用:**
```markdown
See [Section 3.2](#32-version-control) for details.
See [System Architecture](design/architecture/system-architecture.md#5-api-design) for API design.
```

**外部引用:**
```markdown
Reference: PRD v0.5.1 Section 15.1
Related: Database Design v1.0 Section 4.4
```

## 4. 文档评审流程

### 4.1 评审类型

| 类型 | 时机 | 评审人 | 周转时间 |
|------|------|-----------|------------|
| Self-Review | Before submission | Author | 即时 |
| 同行评审 | 初稿 | 2 名同行 | 2 天 |
| 技术评审 | 技术文档 | 技术负责人 + 主题专家 | 3 天 |
| Stakeholder Review | Major docs | 所有干系人 | 5 days |
| 最终批准 | Before baseline | Approver | 2 days |

### 4.2 评审检查表

**General Checks:**
- [ ] 文档遵循模板
- [ ] 版本号已更新
- [ ] 状态已更新
- [ ] All sections complete
- [ ] No placeholder text
- [ ] Cross-references valid
- [ ] No spelling/grammar errors

**Technical Checks:**
- [ ] Technically accurate
- [ ] No contradictions with other docs
- [ ] All requirements covered
- [ ] All edge cases addressed
- [ ] Examples provided where needed

**一致性检查:**
- [ ] Terminology consistent with glossary
- [ ] 遵循命名规范
- [ ] 全篇格式一致
- [ ] Cross-references accurate

### 4.3 评审反馈格式

```markdown
## Review Comments

### [Reviewer Name] - [Date]

**Overall Assessment:** [Approve / Approve with Changes / Reject]

**Comments:**

1. **Section X.Y:** [Comment]
   - **Severity:** [Critical / Major / Minor / Suggestion]
   - **Suggestion:** [How to fix]

2. **Section X.Z:** [Comment]
   - **Severity:** [Major]
   - **Suggestion:** [How to fix]

**Action Items:**
- [ ] Fix item 1 (Owner: [Name], Due: [Date])
- [ ] Fix item 2 (Owner: [Name], Due: [Date])
```

## 5. 文档维护

### 5.1 更新触发条件

| Trigger | Action | Responsible |
|---------|--------|-------------|
| PRD 变更 | Update all dependent docs | PM notifies affected owners |
| 设计变更 | Update design docs + impacted specs | Designer/Architect |
| API 变更 | Update API doc + frontend docs | Backend Lead |
| 缺陷修复 | Update relevant docs if behavior changes | Developer |
| 新功能 | Update PRD + design + test docs | Feature owner |

### 5.2 变更控制流程

**For 已基线化 Documents:**

1. **Change Request Submitted**
   - 说明需变更的内容
   - 解释原因
   - 识别受影响的文档

2. **影响分析**
   - 审查受影响的文档
   - 评估风险
   - 估算工作量

3. **Approval**
   - Change request reviewed
   - 已批准/拒绝

4. **Implementation**
   - Make changes
   - Update version
   - Update cross-references

5. **Verification**
   - 审查变更
   - 验证一致性
   - Update status

### 5.3 文档审计

**Frequency:** Monthly

**Audit Checklist:**
- [ ] All documents accessible
- [ ] No orphaned documents
- [ ] Cross-references valid
- [ ] 已维护版本历史
- [ ] 状态准确
- [ ] No stale documents (> 90 days without review)

## 7. 门禁输出控制

### 7.1 输出校验规则

**Document Output:**
- Must pass template validation
- Must have valid cross-references
- Must use standard terminology
- Must be spell-checked

**Code Output:**
- Must pass linting
- Must have tests
- Must have documentation
- Must pass code review

**Design Output:**
- Must follow design system
- Must be accessible
- Must be responsive
- Must be reviewed

### 7.2 阻断规则

| 条件 | 被阻断的输出 | 解决方式 |
|-----------|---------------|------------|
| Missing required section | 文档提交 | Add section |
| Invalid cross-reference | 文档基线化 | 修复引用 |
| Code coverage < 80% | Merge to main | Add tests |
| Critical defect open | Release | Fix defect |
| 未达成性能目标 | Release | Optimize |

### 7.3 例外流程

**申请例外:**
1. 记录例外
2. 解释原因 gate cannot be passed
3. 评估风险 of proceeding
4. Propose mitigation
5. Get approval from approver

**例外批准人:**
- Technical exceptions: Tech Lead
- 流程例外：PM
- 安全例外：安全负责人
