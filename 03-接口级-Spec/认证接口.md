> 依赖文档：01-系统级-Spec/API总览.md、02-模块级-Spec/模块-01-账户与项目管理.md、03-接口级-Spec/表结构详细设计.md（User / Role 表）

## 1. 概述

认证接口负责用户身份校验与令牌（Token）生命周期管理，是全部业务接口的访问前提。采用 **JWT（Access + Refresh 双令牌）** 机制：

- 所有受保护接口须在请求头携带 `Authorization: Bearer {access_token}`。
- 4 种角色（admin / project_manager / engineer / viewer）的权限校验由 RBAC 中间件统一处理，角色定义存储于 `Role` 表，用户-角色关系经 `User.role_id` 关联。

### 1.1 端点总览（附录D 权威清单）

| 方法 | 路径 | 说明 | 鉴权 |
|------|------|------|------|
| POST | `/api/v1/auth/login` | 用户名密码登录，签发双 Token | 否 |
| POST | `/api/v1/auth/logout` | 注销，使 Refresh Token 失效 | 否（持 refresh_token） |
| POST | `/api/v1/auth/refresh` | 用 Refresh Token 换取新 Access Token | 否（持有效 refresh_token） |
| GET | `/api/v1/auth/me` | 获取当前登录用户信息 | 是 |

## 2. Token 机制

### 2.1 令牌规格

| 令牌 | 算法 | 生命周期（TTL） | 存储位置 | 用途 |
|------|------|----------------|----------|------|
| access_token | JWT HS256 | **900 秒（15 分钟）** | 客户端内存（建议不持久化） | 业务接口鉴权 |
| refresh_token | JWT HS256 | **7 天（604800 秒）** | 客户端持久化（httpOnly Cookie 或安全存储） | 换取新 access_token；含 `jti` 声明用于黑名单 |

- `expires_in` 字段单位：秒（值为 `900`）。
- `token_type` 固定为 `Bearer`。
- 两个令牌的 `jti`（JWT ID）由服务端生成并持久化，作为黑名单失效控制的键。

### 2.2 登录签发流程

```
1. 客户端 POST /api/v1/auth/login 提交 username + password
2. 服务端校验凭证（密码哈希比对，参考 User.password_hash）
3. 校验失败 → 401 INVALID_CREDENTIALS
4. 校验成功 → 生成 access_token(900s) 与 refresh_token(7d)，各带独立 jti
5. 返回双 Token + expires_in + user 概要（id/username/email/role/full_name）
```

### 2.3 刷新流程（F1-004 无感续期）

```
T0  客户端持 access_token(A0, expires_at=T0+15min) 调业务接口
T1  业务接口返回 401 TOKEN_EXPIRED（A0 已过期）
T2  客户端拦截器静默调用 POST /api/v1/auth/refresh（携带 refresh_token）
T3  服务端校验 refresh_token：
    - 格式非法 / 签名错误      → 401 INVALID_TOKEN
    - 已列入黑名单（已注销）   → 401 TOKEN_EXPIRED（提示重新登录）
    - 自然过期（>7d）          → 401 TOKEN_EXPIRED
    - 有效                     → 生成新 access_token(A1, 900s)
T4  服务端返回 {access_token:A1, expires_in:900}（不轮换 refresh_token，见 O-1）
T5  客户端用 A1 重放原业务请求 → 成功
T6  若 T3 返回 401（refresh 也失效）→ 跳转登录页，提示「登录已过期，请重新登录」
```

> 并发去重：多个业务请求同时遇到 401 时，前端应将 refresh 请求合流（同一时刻只发一个 `/auth/refresh`），其余请求排队等待新 access_token 后重放。

### 2.4 登出与失效策略（黑名单）

```
1. 客户端 POST /api/v1/auth/logout 提交 refresh_token
2. 服务端解析 refresh_token 的 jti，写入黑名单：
   - 存储：Redis SET  key=jti:{jti}  value=1  EX=剩余 TTL（自然过期自动清理）
3. 后续任何使用「该 refresh_token 换新」的请求被拒
4. 返回 204 No Content
```

- **access_token 不主动失效**：因其 TTL 仅 15 分钟，依赖自然过期；注销仅使 refresh_token 失效，已签发的短 access 在过期前仍可用（风险窗口 ≤15 分钟）。

## 3. 端点详细设计

### 3.1 POST /api/v1/auth/login

**请求体**

| 字段 | 类型 | 必填 | 校验规则 |
|------|------|------|----------|
| username | string | 是 | 非空；对应 `User.username`（或 email，见 O-3） |
| password | string | 是 | 非空，长度 ≥ 8 |

```json
{
  "username": "engineer@example.com",
  "password": "secure_password"
}
```

**响应 200**

```json
{
  "success": true,
  "data": {
    "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
    "refresh_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
    "token_type": "Bearer",
    "expires_in": 900,
    "user": {
      "id": 1,
      "username": "engineer@example.com",
      "email": "engineer@example.com",
      "role": "engineer",
      "full_name": "John Doe"
    }
  }
}
```

> `expires_in` 字段单位为秒，值固定 `900`（与 access_token TTL 一致）；客户端据此设置定时刷新。

**响应 401**

```json
{
  "success": false,
  "error": {
    "code": "INVALID_CREDENTIALS",
    "message": "账号或密码错误"
  }
}
```

**错误码**：`400 VALIDATION_ERROR`（username/password 缺失或为空）。

### 3.2 POST /api/v1/auth/refresh

**请求体**

| 字段 | 类型 | 必填 | 校验规则 |
|------|------|------|----------|
| refresh_token | string | 是 | 非空 JWT 字符串 |

```json
{ "refresh_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..." }
```

**响应 200**

```json
{
  "success": true,
  "data": {
    "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
    "token_type": "Bearer",
    "expires_in": 900
  }
}
```

> 续期响应明确返回 `expires_in`，客户端据此重置定时器；不轮换 refresh_token（见 O-1）。

**错误码**

| HTTP | code | 触发条件 |
|------|------|----------|
| 400 | VALIDATION_ERROR | refresh_token 缺失 |
| 401 | INVALID_TOKEN | refresh_token 格式/签名错误 |
| 401 | TOKEN_EXPIRED | refresh_token 已注销（黑名单）或已自然过期 |

### 3.3 POST /api/v1/auth/logout

**请求体**

| 字段 | 类型 | 必填 | 校验规则 |
|------|------|------|----------|
| refresh_token | string | 是 | 非空 JWT 字符串 |

**响应 204**：No Content（无响应体）。

**错误码**：`400 VALIDATION_ERROR`（refresh_token 缺失）、`401 INVALID_TOKEN`（格式/签名错误）。

> 注销幂等：重复注销同一 refresh_token（已黑名单）仍返回 204。

### 3.4 GET /api/v1/auth/me（新增）

获取当前登录用户的完整信息（含角色权限矩阵），用于前端初始化权限路由、菜单可见性判断、个人中心展示。

**请求**：无 body，须在 Header 携带 `Authorization: Bearer {access_token}`。

**响应 200**

```json
{
  "success": true,
  "data": {
    "id": 1,
    "username": "engineer@example.com",
    "email": "engineer@example.com",
    "full_name": "John Doe",
    "role": {
      "id": 3,
      "code": "engineer",
      "name": "暖通工程师",
      "permissions": [
        "project:view", "project:edit",
        "building:create", "building:edit",
        "room:create", "room:edit", "room:delete", "room:copy",
        "calc:static", "calc:dynamic", "calc:preview",
        "export:static", "export:equipment", "export:calc-book", "export:dynamic"
      ]
    },
    "project_ids": [1, 2, 5],
    "last_login_at": "2026-07-14T08:30:00Z",
    "created_at": "2026-01-15T10:00:00Z"
  }
}
```

**字段说明**

| 字段 | 类型 | 来源 | 说明 |
|------|------|------|------|
| id | int | `User.id` | 用户主键 |
| username | string | `User.username` | 登录名 |
| email | string | `User.email` | 邮箱 |
| full_name | string | `User.full_name` | 显示名 |
| role.id | int | `Role.id` | 角色 ID |
| role.code | string | `Role.code` | 角色编码（admin/project_manager/engineer/viewer） |
| role.name | string | `Role.name` | 角色中文名 |
| role.permissions | string[] | `Role.permissions`（JSON 数组） | 权限点列表，前端据此控制按钮/菜单可见性 |
| project_ids | int[] | 项目成员关系（F1-026 数据隔离） | 当前用户可见的项目 ID 列表 |
| last_login_at | datetime | `User.last_login_at` | 最近登录时间 |

**错误码**

| HTTP | code | 触发条件 |
|------|------|----------|
| 401 | TOKEN_EXPIRED | access_token 已过期（前端走 refresh 流程后重试） |
| 401 | INVALID_TOKEN | access_token 格式/签名错误 |
| 404 | RESOURCE_NOT_FOUND | 用户已被禁用或删除 |

> 此端点常被前端在应用启动时调用一次，结果缓存在 `AuthContext`（见状态管理.md §3）。`role.permissions` 数组与 RBAC 中间件用的权限点保持一致。

## 4. 通用错误码

| code | HTTP | 含义 |
|------|------|------|
| INVALID_CREDENTIALS | 401 | 用户名或密码错误 |
| TOKEN_EXPIRED | 401 | access/refresh token 已过期或已注销 |
| INVALID_TOKEN | 401 | token 格式/签名非法 |
| VALIDATION_ERROR | 400 | 输入校验失败 |
| INTERNAL_ERROR | 500 | 服务端意外错误 |

## 5. 待确认 / 开放问题

- **O-1 Refresh Token 是否轮换**：当前 refresh 响应仅返回新 access_token，未返回新 refresh_token。是否采用「刷新即轮换 refresh_token」策略（轮换可提升安全性，但要求客户端更新存储）待确认。**当前基线：不轮换。**
- **O-2 登录标识字段**：username 是否同时接受 email 登录待确认（API 示例为 email 形式，但字段名为 username）。
- **O-3 黑名单存储**：采用 Redis 为推荐实现；若运行环境无 Redis，需确认降级方案。
