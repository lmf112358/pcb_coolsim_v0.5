## 1. 概述

认证接口负责用户身份校验与令牌（Token）生命周期管理，是全部业务接口的访问前提。采用 **JWT（Access + Refresh 双令牌）** 机制：

- 所有受保护接口须在请求头携带 `Authorization: Bearer {access_token}`（见 API总览 §1.2）。
- 4 种角色（admin / project_manager / engineer / viewer）的权限校验在 API总览 §1.1 定义，本文件仅描述令牌本身。
- 本批次不含「天气 / 设置 / WebSocket / 对话采集」接口（见任务范围说明）。

---

## 2. 端点总览

| 方法 | 路径 | 说明 | 鉴权 |
|------|------|------|------|
| POST | `/api/v1/auth/login/` | 用户名密码登录，签发双 Token | 否 |
| POST | `/api/v1/auth/refresh/` | 用 Refresh Token 换取新 Access Token | 否（持有效 refresh_token） |
| POST | `/api/v1/auth/logout/` | 注销，使 Refresh Token 失效 | 否（持 refresh_token） |

> 说明：login/refresh/logout 三个端点本身不需要已登录态；其他业务端点均需在 Header 携带有效 access_token。

## 3. Token 机制

### 3.1 令牌规格

| 令牌 | 算法 | 生命周期（TTL） | 存储位置 | 用途 |
|------|------|----------------|----------|------|
| access_token | JWT HS256 | **900 秒（15 分钟）** | 客户端内存（建议不持久化） | 业务接口鉴权 |
| refresh_token | JWT HS256 | **7 天（604800 秒）** | 客户端持久化（httpOnly Cookie 或安全存储） | 换取新 access_token；含 `jti` 声明用于黑名单 |

- `expires_in` 字段单位：秒（与 API总览 §2.1 一致，值为 `900`）。
- `token_type` 固定为 `Bearer`。
- 两个令牌的 `jti`（JWT ID）由服务端生成并持久化，作为黑名单失效控制的键。

### 3.2 登录签发流程

```
1. 客户端 POST /auth/login/ 提交 username + password
2. 服务端校验凭证（密码哈希比对）
3. 校验失败 → 401 INVALID_CREDENTIALS
4. 校验成功 → 生成 access_token(900s) 与 refresh_token(7d)，各带独立 jti
5. 返回双 Token + user 概要（id/username/email/role/full_name）
```

### 3.3 刷新流程（对应 F1-004 无感续期）

```
1. access_token 过期（或即将过期），客户端持 refresh_token 调用 POST /auth/refresh/
2. 服务端校验 refresh_token：
   - 格式非法 / 签名错误      → 401 INVALID_TOKEN
   - 已列入黑名单（已注销）   → 401 TOKEN_EXPIRED（提示重新登录）
   - 自然过期（>7d）          → 401 TOKEN_EXPIRED
   - 有效                     → 生成新 access_token(900s)
3. 返回新 access_token + expires_in（不轮换 refresh_token，见开放问题 O-1）
```

> 前端实现「无感续期」：拦截 401 TOKEN_EXPIRED 且 refresh 仍有效时静默调用 refresh；若 refresh 也失效则跳转登录页并提示「登录已过期，请重新登录」（F1-004 验收标准）。

### 3.4 登出与失效策略（黑名单）

```
1. 客户端 POST /auth/logout/ 提交 refresh_token
2. 服务端解析 refresh_token 的 jti，写入黑名单：
   - 存储：Redis SET  key=jti:{jti}  value=1  EX=剩余 TTL（自然过期自动清理）
3. 后续任何使用「该 refresh_token 换新」或「黑名单 access 复用」的请求被拒
4. 返回 204 No Content
```

- **access_token 不主动失效**：因其 TTL 仅 15 分钟，依赖自然过期；注销仅使 refresh_token 失效，已签发的短 access 在过期前仍可用（风险窗口 ≤15 分钟，符合 v0.5.1 设计）。
- 若需「注销即全失效」，可将 access_token 的 jti 一并列入黑名单（待确认 O-2）。

## 4. 端点详细设计

### 4.1 POST /api/v1/auth/login/

**请求体**

| 字段 | 类型 | 必填 | 校验规则 |
|------|------|------|----------|
| username | string | 是 | 非空；对应 User.username（或 email，见 O-3） |
| password | string | 是 | 非空，长度 ≥ 8（与账户策略一致） |

```json
{
  "username": "engineer@example.com",
  "password": "secure_password"
}
```

**响应 200**（同 API总览 §2.1）

```json
{
  "success": true,
  "data": {
    "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
    "refresh_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
    "token_type": "Bearer",
    "expires_in": 900,
    "user": {
      "id": 1,
      "username": "engineer@example.com",
      "email": "engineer@example.com",
      "role": "engineer",
      "full_name": "John Doe"
    }
  }
}
```

**响应 401**

```json
{
  "success": false,
  "error": {
    "code": "INVALID_CREDENTIALS",
    "message": "Invalid username or password"
  }
}
```

**校验规则**：username 或 password 缺失/为空 → `400 VALIDATION_ERROR`。

### 4.2 POST /api/v1/auth/refresh/

**请求体**

| 字段 | 类型 | 必填 | 校验规则 |
|------|------|------|----------|
| refresh_token | string | 是 | 非空 JWT 字符串 |

```json
{ "refresh_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..." }
```

**响应 200**

```json
{
  "success": true,
  "data": {
    "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
    "expires_in": 900
  }
}
```

**错误码**

| HTTP | code | 触发条件 |
|------|------|----------|
| 400 | VALIDATION_ERROR | refresh_token 缺失 |
| 401 | INVALID_TOKEN | refresh_token 格式/签名错误 |
| 401 | TOKEN_EXPIRED | refresh_token 已注销（黑名单）或已自然过期 |

### 4.3 POST /api/v1/auth/logout/

**请求体**

| 字段 | 类型 | 必填 | 校验规则 |
|------|------|------|----------|
| refresh_token | string | 是 | 非空 JWT 字符串 |

```json
{ "refresh_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..." }
```

**响应 204**：No Content（无响应体）。

**错误码**

| HTTP | code | 触发条件 |
|------|------|----------|
| 400 | VALIDATION_ERROR | refresh_token 缺失 |
| 401 | INVALID_TOKEN | refresh_token 格式/签名错误 |

> 注销幂等：重复注销同一 refresh_token（已黑名单）仍返回 204。

## 5. 通用错误码（复用 API总览 §1.3 + 附录）

| code | HTTP | 含义 |
|------|------|------|
| INVALID_CREDENTIALS | 401 | 用户名或密码错误 |
| TOKEN_EXPIRED | 401 | access/refresh token 已过期或已注销 |
| INVALID_TOKEN | 401 | token 格式/签名非法 |
| VALIDATION_ERROR | 400 | 输入校验失败 |
| INTERNAL_ERROR | 500 | 服务端意外错误 |

## 6. 待确认 / 开放问题

- **O-1 Refresh Token 是否轮换**：API总览 §2.2 刷新响应仅返回新 access_token，未返回新 refresh_token。需确认是否采用「刷新即轮换 refresh_token」策略（轮换可提升安全性，但要求客户端更新存储）。
- **O-2 注销是否连带失效 access_token**：当前设计 access_token 依赖 15 分钟自然过期；是否需要黑名单同时收纳 access_token jti 以实现「注销即全失效」待确认。
- **O-3 登录标识字段**：username 是否同时接受 email 登录待确认（API总览 示例为 email 形式，但字段名为 username）。
- **O-4 黑名单存储**：采用 Redis 为推荐实现，若运行环境无 Redis，需确认降级方案（如数据库黑名单表——但 15 表锚点未含此表，需评估是否新增）。
