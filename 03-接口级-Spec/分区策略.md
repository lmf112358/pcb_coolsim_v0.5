## 1. 概述

本文档给出大数据量场景下的分区策略，重点是 **8760h 逐时数据**与**大结果集表**。依据系统架构设计 §1（Data Layer 含 TimescaleDB 扩展，承载 8760h 气象 / 时间序列）与数据库设计 §4 的结果表结构。

**核心事实澄清（重要）**：
- 数据库设计 §4 的 15 张表中，`room_load_result`/`room_air_volume_result`/`room_load_summary`/`load_summary` 均为**按 (room, season) 或按层级的设计日聚合结果**，**不含逐时（hour）列**，不是 8760h 数据。
- **8760h 逐时数据**来自动态仿真（模块-06），在系统架构设计中明确由 **TimescaleDB（hypertable）** 承载（气象数据 + 仿真逐时结果），**该表不在 15 张关系表之内**。
- 因此分区策略分两层：① 关系结果表按 `project_id` 范围分区（§4）；② 逐时时间序列按 `time` + `project_id` 在 TimescaleDB 建 hypertable（§5）。

---

## 2. 分区目标与原则

| 原则 | 说明 |
|------|------|
| 查询局部性 | 所有业务查询按 `project_id` 隔离（数据隔离 §6.3），分区键首选 `project_id` |
| 时间局部性 | 逐时数据按时间范围冷热分离、快速剪枝 |
| 维护可控 | 分区可独立 `ATTACH`/`DETACH`、单独 `VACUUM`、按保留期 `DROP` |
| 不破坏唯一约束 | 复合唯一键须包含分区键（见 §4.3） |

## 3. 关系结果表：按 project_id 范围分区

### 3.1 适用表

结果集随房间数 × 季节数 × 水温档数增长。对 1000 房间 × 3 季节 × 2 水温 ≈ 6000 行/表，单项目可控；但多项目长期累积需分区：

- `load_summary`（聚合表，增长最快，优先分区）
- `room_load_result` / `room_air_volume_result`（每房间每季节一行）
- `room_load_summary`（每房间每季节每水温一行）

`project`/`building`/`floor`/`room`/`city_config`/`conversation_session`/`extra_load` 等体量小或本就按项目过滤，默认不分区。

### 3.2 分区键与实现（PostgreSQL 原生声明式分区）

```sql
-- 以 load_summary 为例：按 project_id 做 RANGE 分区
CREATE TABLE load_summary (
    id BIGINT GENERATED ALWAYS AS IDENTITY,
    project_id BIGINT NOT NULL REFERENCES project(id) ON DELETE CASCADE,
    building_id BIGINT REFERENCES building(id) ON DELETE CASCADE,
    floor_id BIGINT REFERENCES floor(id) ON DELETE CASCADE,
    season_id BIGINT NOT NULL REFERENCES season_config(id),
    water_temp_config_id BIGINT REFERENCES water_temperature_config(id) ON DELETE SET NULL,
    scope VARCHAR(20) NOT NULL,
    category VARCHAR(50) NOT NULL,
    fresh_air_load DECIMAL(12,4),
    terminal_load DECIMAL(12,4),
    extra_load DECIMAL(12,4),
    total_load DECIMAL(12,4) NOT NULL,
    created_at DATETIME NOT NULL,
    updated_at DATETIME NOT NULL,
    CONSTRAINT uniq_ls UNIQUE (project_id, building_id, floor_id, season_id, water_temp_config_id, scope, category)
) PARTITION BY RANGE (project_id);

CREATE TABLE load_summary_p1 PARTITION OF load_summary FOR VALUES FROM (1) TO (1000);
CREATE TABLE load_summary_p2 PARTITION OF load_summary FOR VALUES FROM (1000) TO (2000);
```

### 3.3 分区创建 / 迁移

- **初始**：少量分区覆盖预期 project_id 区间；超出后 `CREATE PARTITION` 追加（如每 1000 项目一区）。
- **迁移已有数据**：若上线后从非分区表迁移，用 `CREATE TABLE ... (LIKE ... INCLUDING ALL) PARTITION BY RANGE` + `INSERT INTO new SELECT * FROM old` + 改名原子切换。
- **分区管理自动化**：用 `pg_partman` 扩展按期/按 ID 自动建/删分区，避免手工维护。

### 3.4 对查询性能的影响

- **正向**：模式 B（按 project 聚合）查询自动剪枝到单分区；`ATTACH`/`DETACH` 让历史项目归档零锁表。
- **负向**：跨项目报表需扫多分区（本项目无此场景，数据隔离禁止跨项目）；唯一约束含分区键而变宽，写入略增。

## 4. 逐时时间序列：TimescaleDB hypertable（按时间 + 项目）

### 4.1 表定位

动态仿真逐时结果（模块-06 §6.1 `simulation_result`）含 `datetime/year/hour_of_year/outdoor_temp/.../total_load`，属典型时间序列。按系统架构设计放 TimescaleDB：

```sql
CREATE TABLE simulation_result (
    project_id BIGINT NOT NULL REFERENCES project(id) ON DELETE CASCADE,
    room_id BIGINT NOT NULL REFERENCES room(id) ON DELETE CASCADE,
    simulation_date TIMESTAMP NOT NULL,
    year INTEGER,
    hour_of_year INTEGER,
    outdoor_temp DECIMAL(5,2),
    outdoor_humidity DECIMAL(5,2),
    outdoor_enthalpy DECIMAL(10,2),
    terminal_load DECIMAL(12,2),
    fresh_air_load DECIMAL(12,2),
    total_load DECIMAL(12,2),
    simulation_type VARCHAR(20),
    created_at TIMESTAMP DEFAULT NOW()
) WITH (timescaledb.hypertable,
        time_column_name 'simulation_date',
        partitioning_column 'project_id',
        number_partitions 4);
```

### 4.2 分区键选择

- **时间维度**：`simulation_date` → 按时间块（chunk）自动切分（默认 7 天/块，可配）。8760h×3 年 = 26280 行/房间，时间分块让"按年/月/日"聚合（API §7.5 `aggregation=hourly|daily|monthly`）仅扫相关 chunk。
- **项目维度**：`project_id` 作为复合分区列，使单项目查询落在少数子分区；与数据隔离一致。

### 4.3 查询性能影响

| 查询 | 命中 | 效果 |
|------|------|------|
| `GET /calculations/dynamic/{pid}/?year=2024` | 时间分块 + project 子分区 | 仅扫 2024 chunk，毫秒级 |
| `?room_id=1&aggregation=daily` | room_id 索引 + 时间分块 | 下采样聚合快 |
| 负荷曲线 Zoom（年→月→日） | 时间分块剪枝 | 交互流畅（架构 §7.1：动态仿真 < 30s） |

### 4.4 保留与压缩

- **保留策略**：`add_retention_policy('simulation_result', INTERVAL '3 years')` 自动清理超期 chunk。
- **压缩**：`add_compression_policy` 对历史 chunk 列存压缩（total_load 等数值列压缩比高）。

## 5. 气象数据分区（TimescaleDB）

气象数据（API §8）同属 8760h 时间序列，按 `city_id` + `datetime` 建 hypertable：

```sql
CREATE TABLE weather_data (
    city_id BIGINT NOT NULL REFERENCES city_config(id) ON DELETE RESTRICT,
    datetime TIMESTAMP NOT NULL,
    dry_bulb_temp DECIMAL(5,2),
    wet_bulb_temp DECIMAL(5,2),
    relative_humidity DECIMAL(5,2),
    atmospheric_pressure DECIMAL(10,2),
    wind_speed DECIMAL(4,1),
    solar_radiation DECIMAL(8,2)
) WITH (timescaledb.hypertable, time_column_name 'datetime',
        partitioning_column 'city_id', number_partitions 4);
```

- **命中**：模式 C「按城市查气象」`WHERE city_id=? AND datetime BETWEEN ? AND ?` 走时间分块 + 城市子分区。

## 6. 分区对写入/计算的影响

- **批量计算**：静态批量（`calculate_project_static`）走 `executemany`/`COPY`，分区表写入分散到各分区，无热点。
- **动态仿真**：Celery worker 流式写 chunk（模块-06 §4.3 批插 1000 行），TimescaleDB 按时间块追加，顺序写友好。
- **索引**：分区表本地索引随分区创建；`pg_partman` 自动维护。

## 7. 待确认

1. **逐时表是否在 15 表 schema 内**：本文档按架构设计将 `simulation_result`/`weather_data` 视为 TimescaleDB 扩展表，**不属于 15 张关系表**。若要求归入关系 schema，需新增实体——**待确认**（奥卡姆剃刀：沿用架构设计既有划分，不新增关系表）。
2. **关系结果表是否实际分区**：单项目数据量通常可控，是否对 `load_summary` 等启用 `project_id` 分区，取决于部署规模——**建议大客户/多租户场景启用，单项目场景可暂缓**。
3. **分区粒度**：`project_id` RANGE 每区跨度（1000？按租户？）——**待确认**。
4. **TimescaleDB 可用性**：部署环境是否含 TimescaleDB 扩展；若仅纯 PostgreSQL，逐时表退化为按 `(project_id, datetime)` 的 `RANGE` 原生分区（失去自动 chunk/压缩）。
