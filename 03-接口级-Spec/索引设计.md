## 1. 概述

本文档在 `数据库设计.md` §5 基础上，给出可直接落库的索引 DDL 与**命中说明**，覆盖主键、外键、复合、全文四类索引。目标：支撑三类典型查询模式（§4）——

- **模式 A**：项目下建筑/楼层/房间列表（层级展开）
- **模式 B**：负荷汇总多级聚合（floor/building/project）
- **模式 C**：按城市查气象/室外参数

数据库为 PostgreSQL 16（系统架构设计 §2.2）。全文检索需求弱，统一用 `pg_trgm` trigram 索引满足模糊搜索（城市名、房间名）；不引入独立全文引擎。

---

## 2. 主键索引

所有 15 张表均以 `id BIGINT` 自增为主键，PostgreSQL 自动建立 `PRIMARY KEY` 唯一 B-tree 索引。无需手写。

---

## 3. 外键索引（必建）

外键列若不建索引，级联删除/更新会全表扫描父子表。下列索引与 §5.2 一致：

| 表 | 索引名 | 字段 | 理由 |
|----|--------|------|------|
| building | idx_building_project | (project_id) | 项目下建筑列表（模式 A） |
| floor | idx_floor_building | (building_id) | 建筑下楼层列表（模式 A） |
| room | idx_room_floor | (floor_id) | 楼层下房间列表（模式 A） |
| water_temperature_config | idx_wtc_project | (project_id) | 项目水温配置 |
| season_config | idx_season_project | (project_id) | 项目季节配置 |
| room_load_parameter | idx_rlp_room / idx_rlp_season | (room_id)/(season_id) | 计算参数回查 |
| room_load_result | idx_rlr_room / idx_rlr_season | (room_id)/(season_id) | 结果回查 |
| room_air_volume_parameter | idx_ravp_room / idx_ravp_season | (room_id)/(season_id) | 参数回查 |
| room_air_volume_result | idx_ravr_room / idx_ravr_season | (room_id)/(season_id) | 结果回查 |

## 4. 复合索引（按典型查询模式）

### 4.1 模式 A：层级展开列表

层级查询恒带父级 ID 过滤，复合索引把过滤+排序合并：

```sql
CREATE UNIQUE INDEX uniq_rlp_room_season  ON room_load_parameter(room_id, season_id);
CREATE UNIQUE INDEX uniq_rlr_room_season  ON room_load_result(room_id, season_id);
CREATE UNIQUE INDEX uniq_ravp_room_season ON room_air_volume_parameter(room_id, season_id);
CREATE UNIQUE INDEX uniq_ravr_room_season ON room_air_volume_result(room_id, season_id);
CREATE UNIQUE INDEX uniq_rls_room_season_wt
    ON room_load_summary(room_id, season_id, water_temp_config_id);
```

- **命中**：`WHERE room_id=? AND season_id=?` 直接命中唯一索引；列表分页 `ORDER BY id` 走索引有序扫描。
- **防重复**：UNIQUE 同时兜底"防止重复录入/计算"（§5.3）。

### 4.2 模式 B：负荷多级聚合

`load_summary` 是聚合查询核心，按 (project, season, scope) 与 (building, season)、(floor, season) 检索：

```sql
CREATE INDEX idx_ls_proj_season_scope ON load_summary(project_id, season_id, scope);
CREATE INDEX idx_ls_building_season    ON load_summary(building_id, season_id);
CREATE INDEX idx_ls_floor_season       ON load_summary(floor_id, season_id);
CREATE INDEX idx_ls_proj_wt            ON load_summary(project_id, water_temp_config_id);
```

- **命中**：项目汇总 `WHERE project_id=? AND season_id=? AND scope='project'` 命中 `idx_ls_proj_season_scope` 前导列；建筑级 `WHERE building_id=? AND season_id=?` 命中 `idx_ls_building_season`。
- **覆盖索引优化**：若前端常需 `category,total_load`，可建 `INCLUDE` 覆盖索引减少回表（PG 11+）：
  `CREATE INDEX idx_ls_proj_scope_cover ON load_summary(project_id, season_id, scope) INCLUDE (category, total_load);`

### 4.3 模式 C：按城市查气象/室外参数

```sql
CREATE INDEX idx_city_name ON city_config(city_name);
```

- **命中**：城市下拉 `WHERE city_name LIKE ?` + `pg_trgm` 见 §6；`project` 经 `city_id` 关联后取室外参数无需额外索引（city_config 为小表，约 300 行，顺序扫描可接受）。

### 4.4 extra_load 复合

```sql
CREATE UNIQUE INDEX uniq_el_proj_bld_season_wt_cat
    ON extra_load(project_id, building_id, season_id, water_temp_config_id, category);
CREATE INDEX idx_el_proj_season_cat ON extra_load(project_id, season_id, category);
CREATE INDEX idx_el_building_season  ON extra_load(building_id, season_id);
```

- **命中**：聚合时按 `(project_id, season_id, category)` 取额外负荷；建筑级按 `building_id` + `season_id` 取 PCW/配电室空调等。

## 5. 全文 / 模糊检索索引

前端树形导航与列表支持按名称搜索（房间名、建筑名、城市名）。PostgreSQL 用 `pg_trgm` 满足中文/混合模糊匹配：

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX idx_room_name_trgm  ON room  USING gin (room_name gin_trgm_ops);
CREATE INDEX idx_building_trgm   ON building USING gin (building_name gin_trgm_ops);
CREATE INDEX idx_city_name_trgm   ON city_config USING gin (city_name gin_trgm_ops);
```

- **命中**：`WHERE room_name ILIKE '%电镀%'` 走 trigram GIN 索引；城市下拉 300 行亦可。
- **替代**：若仅前缀搜索（「电%」），可用 `varchar_pattern_ops` B-tree 更轻量；混合子串搜索选 `pg_trgm`。

> 注：本系统不含"冷站配置/P&ID/水蓄冷"等模块（PRD v0.5.1 已移除），全文检索仅覆盖既有实体名称字段。

## 6. JSON / 半结构化索引

`conversation_session` 的 `stage_status` / `draft_payload` 为 JSON：

```sql
-- 仅当需按阶段状态过滤时建 GIN（默认不建，详见待确认）
CREATE INDEX idx_cs_stage_status ON conversation_session USING gin (stage_status);
```

- **命中**：`WHERE stage_status @> '{"s2_water_temp":"pending"}'` 走 GIN；一般按 `project_id`+`current_stage` 查询已由 §3 标量索引覆盖，无需 GIN。

## 7. 索引维护与代价

| 关注点 | 说明 |
|--------|------|
| 写入代价 | 结果表每次重算 `UPSERT`，索引同步开销可接受（批量走 `executemany`） |
| 重复索引 | 避免对已是复合索引前导列的字段再建单列索引（如 `room_id` 已被 `uniq_*` 覆盖，不另建 `idx_room_id`） |
| 统计信息 | 定期 `ANALYZE`；大表（load_summary）开 `autovacuum` |
| 只读参考表 | city_config 极小，仅保留 `idx_city_name` |

## 8. 待确认

1. `load_summary` 唯一约束（含 scope/category）是否落地为 UNIQUE 索引（见 `表结构详细设计.md` §17）——影响 §4.2 复合索引是否为 UNIQUE。
2. `stage_status`/`draft_payload` GIN 是否必需——取决于是否需按 JSON 内容检索。
3. 前端搜索是否需 `pg_trgm`（依赖 PG 扩展权限）；若禁扩展，退化为 `varchar_pattern_ops` 前缀索引。
4. `room_load_summary` 是否需要 `INCLUDE` 覆盖索引以加速 Tab2 表格展示（取决于列投影）。
