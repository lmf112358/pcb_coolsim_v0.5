## 1. 功能概述

### 1.1 目的

管理用户认证（JWT）、项目增删改查（CRUD）、基于地图的项目仪表盘、城市气象数据关联，以及四角色权限体系。本模块是整个平台的入口与基座。

### 1.2 关键特性

- 基于 JWT 的认证（Access + Refresh 令牌）
- 4 角色权限系统（系统管理员、项目经理、暖通工程师、查看者）
- **细粒度权限码**（5 模块 12 码）：`simulation`（run/config/compare）、`monitor`（view/export）、`report`（view/export）、`equipment`（view/config）、`system`（user:manage/role:manage/param:manage）——作为 F1-029 预留接口的具体化（v1.1）
- **双层权限守卫**：路由级 `ProtectedRoute(roles)` 拦截越权页面访问 + 组件级 `PermissionGuard(permission_code)` 控制按钮/菜单显隐（v1.1）
- 集成城市气象数据的项目 CRUD
- 带项目标点的地图仪表盘（Leaflet + 高德瓦片）
- 项目搜索与筛选
- 项目级数据隔离

### 1.3 v0.5 范围说明

- 用户与角色：系统管理员 / 项目经理 / 暖通工程师 / 查看者（F1-024）
- 气象数据：项目创建后 Celery 异步获取最近 3 年逐时数据（F1-019）
- 项目信息字段：项目名称（必填）、项目编号（否）、所属城市（必填，关联国标参数）、详细地址（否）、项目描述（否）（PRD §5.6）
- 细粒度权限（按建筑/楼层授权）v0.5 仅预留接口，不实现（F1-029）

## 4. 业务逻辑

### 4.1 认证流程（F1-001 / F1-004 / F1-005 / F1-006）

```
登录：
1. 用户提交凭据（F1-001）
2. 校验用户名/密码
3. 生成 Access 令牌（15 分钟）+ Refresh 令牌（7 天）
4. 返回双 Token

令牌刷新（F1-004）：
1. Access 过期 + Refresh 有效 → 自动续期，无感刷新
2. Refresh 失效 → 跳转登录页，提示"登录已过期，请重新登录"

登出（F1-005）：
1. 客户端发送 Refresh 令牌
2. 加入黑名单，返回成功

密码安全（F1-006）：bcrypt 哈希存储，不明文。
```

### 4.2 项目创建流程（F1-015 ~ F1-023）

```
1. 用户提交项目数据（F1-015：名称/地址/城市必填）
2. 校验必填字段
3. 从 CityConfig 查找城市，自动关联国标室外设计参数与经纬度（F1-017）
4. 项目地址填写后在地图标注位置（F1-016）
5. 创建 Project 记录
6. 创建默认 WaterTempConfig（低温 7/12、中温 12/17）（F1-018）
7. 创建 ProjectMember(creator, role=manager)
8. 触发 Celery 任务 fetch_weather_data(project_id)（F1-019）
9. 返回项目 + 气象任务 ID

异步气象获取（F1-019 ~ F1-022）：
1. Celery worker 接收任务
2. 调用外部气象 API（最近 3 年逐时，约 26280~26304 条）
3. 解析并校验（干球/湿球/相对湿度/大气压/风速/太阳辐射）（F1-020）
4. 存入 WeatherRecord 表（同一城市只拉一次，共享）（F1-019）
5. 推送通知"气象数据已就绪"（F1-021）
6. API 失败时项目仍创建成功，状态标"气象数据缺失"，可稍后上传/重拉（F1-022）
```

### 4.3 权限校验流程（F1-024 ~ F1-029）

```
每个 API 请求：
1. 从 Authorization 头提取 JWT
2. 校验签名与过期（F1-025）
3. 加载 User，校验 is_active，预加载 user.roles.permissions
4. 项目级端点：
   a. 检查 User 是否为 ProjectMember（F1-026 项目级数据隔离）
   b. 检查项目级角色权限（manager/engineer/viewer）
5. 细粒度权限码校验（v1.1）：
   a. admin 角色 → 直通（短路，所有权限码默认通过）
   b. 其他角色 → 检查 require_permission(code) 中 code 是否在用户权限集合
6. 允许或拒绝（403 INSUFFICIENT_PERMISSIONS）

角色能力（F1-024）：
- 系统管理员：创建用户/重置密码/分配系统角色（F1-028）、全项目可见、admin 角色权限码直通
- 项目经理：项目内邀请已有账号用户并分配角色（F1-027）
- 暖通工程师：项目内数据录入与计算（simulation:* + monitor:* + report:* + equipment:*）
- 查看者：只读（monitor:view / report:view / equipment:view）

权限码示例（5 模块 12 码）：
  simulation:run | simulation:config | simulation:compare
  monitor:view | monitor:export
  report:view | report:export
  equipment:view | equipment:config
  system:user:manage | system:role:manage | system:param:manage

前端双层守卫（v1.1）：
- 路由级：<ProtectedRoute roles={['admin']}> 拦截 /admin/* 等越权页面
- 组件级：<PermissionGuard permission="system:user:manage"> 包裹按钮/菜单项，按权限码显隐

细粒度权限（按建筑/楼层授权）：v0.5 仅预留接口，不实现（F1-029）
```

## 7. 安全考量

### 7.1 密码安全（F1-006）

- bcrypt 哈希（cost 因子 12）
- 禁止记录或返回密码
- 强制密码复杂度（最少 8 字符，含 1 大写、1 数字、1 特殊字符）

### 7.2 令牌安全（F1-004 / F1-025）

- Access：15 分钟；Refresh：7 天
- **Access token 仅存内存**（不写 localStorage，防 XSS窃取）；刷新页面后丢失，由 refresh 机制重新获取（v1.1）
- **Refresh token 存 HttpOnly Cookie**：`HttpOnly + Secure + SameSite=Strict`，`Path=/api/v1/auth`，防止 JS 读取与 CSRF（v1.1）
- Refresh 哈希入库；登出加入黑名单（删除 Cookie + 失效记录）；使用时轮换
- **401 自动刷新 + 并发请求队列**：前端 Axios 拦截器在收到 401 时，首个请求触发 `POST /auth/refresh/`，期间其他并发的 401 请求排队等待新 token 后统一重放，避免并发刷新风暴（v1.1，详见状态管理实现.md §3.5）

### 7.3 数据隔离（F1-026）

- 项目查询按用户成员资格过滤，禁止跨项目数据泄露
- 基于 URL 的访问校验（无法通过 URL 访问他人项目）

## 13. 原型对照说明（v1.1 新增）

`参考/factory-management-v2.0.5` 原型用 **FastAPI + SQLAlchemy + PyJWT** 实现了一套 RBAC 参考实现（User/Role/Permission 三表 + 12 权限码 + 双层守卫 + access 内存/refresh HttpOnly Cookie + 401 并发刷新队列），并验证了深/浅双主题（antd token 14 组件覆盖）与自研 i18n 方案。

**本模块吸收原型的设计细节**：细粒度权限码体系、双层守卫、Token 安全存储策略、并发刷新队列（见 §1.2、§4.3、§7.2）。

**后端技术栈基线不变**：本平台后端仍为 **Django 5 + DRF + djangorestframework-simplejwt**（见 CLAUDE.md §技术栈与 01-系统级-Spec/技术选型.md），原型 FastAPI 实现仅作 RBAC 字段/权限码/Token 安全策略的设计参考，不作技术栈基线。原因：原型后端仅实现 RBAC 三表，无业务表；业务模块（模块 4-10 的计算/仿真/8760h/导出）依赖 Django+Celery+TimescaleDB 成熟生态。
