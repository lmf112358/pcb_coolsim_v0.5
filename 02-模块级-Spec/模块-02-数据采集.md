## 1. 模块概述

### 1.1 目的
负责采集系统所需的全部输入数据：建筑参数（功能区域面积、高度、温湿度要求、负荷指标、冷冻水档归属等）与图纸数据（设计院提供的楼层平面 PDF 图纸）。为下游静态 / 动态计算提供唯一、一致的数据源。

### 1.2 三种录入通道
模块二提供**三种同源录入通道**，共享同一数据模型（项目 → 建筑 → 楼层 → 功能区域 + 区域参数），结果互相可见、互不覆盖：

| 通道 | 入口 | 适用场景 | PRD |
| --- | --- | --- | --- |
| 树形导航（Tab1） | 工作台 Tab1 基础配置，左树右详情 | 熟悉字段、精确逐项录入 | §6.2 ~ §6.7 |
| Excel 批量导入 | Tab1「下载模板 / 上传」 | 设计院算书批量录入 | §6.8 |
| 对话式采集 | Tab1 顶部「对话式采集」按钮 → 全屏三栏页 | 自然语言、被引导、首次建项 / 数据零散 | §6.10（v0.5.1 新增） |

### 1.3 相关 PRD 需求
- 树形 / 表单：F2-001 ~ F2-045
- Excel 导入：F2-032 ~ F2-039
- 默认值继承：F2-040 ~ F2-045
- 额外负荷：F2-027 ~ F2-031
- 对话式采集：F2-046 ~ F2-061（详见 §3）

## 2. 架构设计

### 2.1 组件结构
```
Frontend (workbench-module)
├── TreeNav       左树：项目→建筑→楼层→功能区域，四级虚拟滚动
├── DetailForm     右详情：7 组字段，实时自动保存（间隔 30s）
├── ExcelImport    模板下载 / 上传解析 / 结果反馈
└── ConversationUI 三栏：阶段导航 / 对话主区 / 结构化侧栏   ← v0.5.1 新增
Backend (projects app)
├── building / floor / room        CRUD
├── extra_load                    CRUD
├── excel_import                 解析 + 四类校验
└── conversation                 session 持久化 + 意图抽取 + SOP 驱动
Shared
├── validators   输入校验：必填 / 范围 / 重复 / 类型
└── defaults      多级默认值继承
```

### 2.2 数据流
```
用户输入（树形 / Excel / 对话）
   ↓ 同一数据模型
building → floor → room（Room 单表，负荷/风量/温湿度/新风/末端档全直存）+ extra_load
   ↓ 实时预览（< 500ms，仅 UI 瞬时值，不落库）
计算阶段（模块四）落 RoomCalcResult / RoomLoadByWaterTemp / LoadSummary
```
> 对话通道采用**逐区域提交 / 保存即落库**，与 Tab1 一致；⑥ 汇总预览仅做校验与确认（详见 §3.2）。

## 3. 对话式采集专项（v0.5.1 新增）

### 3.1 SOP 六阶段
系统主动连续提问，用户以自然语言或快捷芯片作答；每阶段结束输出结构化摘要确认，再进入下一阶段。SOP 与现有字段严格对应（详见 PRD §6.10.2）：

| 阶段 | 采集内容 | 对应数据模型 |
| --- | --- | --- |
| ① 项目基本信息（展示确认） | 展示已建项目信息；支持确认 / 修正 | `Project`（城市与气象已在地图页关联，此处不重复采集） |
| ② 冷冻水温度配置 | 名称、供 / 回水温度；预置低 / 中温 | `water_temperature_config` |
| ③ 建筑结构信息 | 建筑：名称 / 编号 / 描述；楼层：名称 / 面积 / 层高 | `building` / `floor` |
| ④ 功能区域参数 | 逐区域 7 组字段 | `room` |
| ⑤ 额外负荷信息 | 负荷类别 / 值 / 关联水温 / 备注 | `extra_load` |
| ⑥ 汇总预览与确认 | 完整性校验、按建筑 / 水温汇总、静态冷量预览、导出、确认入库 | `RoomCalcResult` / `LoadSummary` |

### 3.2 写入语义（v0.5.1 统一）
- ②~⑥ 阶段：**逐区域提交 / 保存即落库**，与 Tab1 手填语义一致（F2-060「一次性写入」与 F2-058「保存退出」统一理解为「每次确认即事务落库」）。
- ⑥ 汇总预览：**仅校验与确认**，不重复写库；确认后标记该区域 / 项目完成。
- 对话与 Tab1 / Excel 为同一数据集两种通道，**互不覆盖、可混合使用**（F2-061）。

### 3.3 断点续采
- 会话状态由 `conversation_session` 表持久化（后端），记录 `current_stage` 与 `stage_status`、`draft_payload`（字段定义见数据库设计 §4.15）。
- 对话采集的房间先以 `room.status = draft` 暂存，确认后转 `active`（F2-057 / F2-058）。
- 刷新或重开浏览器后从上次未完成节点继续（服务端持久化）。

### 3.4 与 Tab1 / Excel 的关系
- 对 Tab1 / Excel 已录入的数据，对话可在缺失节点**续采、补缺**。
- 对话产出的数据立即在 Tab1 树形详情可见并可复核微调（F2-060）。
- Excel「覆盖导入」为显式覆盖操作，与「对话 ↔ Tab1 互不覆盖」不冲突（覆盖仅发生在用户主动选择 Excel 覆盖时）。

### 3.5 对话引擎与状态机实现要点（v0.5.1 补充，吸收类cursor原型）

SOP 六阶段内容不变（见 §3.1），本节仅规范引擎实现要点：

- **状态机驱动（后端）**：SOP 由 `ConversationService` + `SopDriverService` 驱动（见服务层设计.md），每个阶段实现 `ask → parse(用户输入) → after(字段回写 + 下一阶段)` 钩子；前端 `ConversationFlow` 组件仅负责渲染系统提问、发送用户作答、展示返回的结构化字段，**不承载 SOP 状态**（避免前端状态与服务端 session 漂移）。
- **快捷芯片（Chip）**：每阶段预设高频作答芯片，一键填充发送。示例：
  - 阶段②「冷冻水温度配置」：`低温 7/12°C`、`中温 12/17°C`、`自定义`；
  - 阶段④「功能区域参数」：洁净度 `ISO7 / ISO7.5 / ISO8`、温控精度 `±1°C / ±2°C`、压差 `正压 / 负压`。
  芯片由后端按阶段返回（在 `assistant_message.payload.chips` 中），便于后续调整不需前端发版。
- **命令式跳转**：用户输入「修改建筑信息 / 回退 / 重新开始 / 跳过本阶段 / 查看摘要」等指令，由 `IntentExtractionService` 识别（规则匹配优先，预留 LLM 接口）后驱动 `SopDriverService` 跳转或回退阶段（对应 F2-049 容错、F2-057 断点续采）。
- **SummaryCard 四动作**（阶段结束确认卡片）：`确认 / 修改 / 跳过 / 稍后`，分别对应「提交本阶段落库」「回到本阶段修改」「标记 skipped 进入下一阶段」「保存退出稍后继续」（F2-051 / F2-058）。
- **ToolCard 状态点**：异步工具结果（气象拉取、Excel 解析、实时预览）用三态视觉反馈——`running`（主色脉冲）/ `ok`（成功色对勾）/ `fail`（危险色叉号），与设计系统 §5.9 语义色对齐。
- **进度条**：顶栏显示六阶段整体进度（已完成/总数），点已完成阶段节点可回看（只读）或回退修改。

### 3.6 断点续采的前端兜底

- 服务端持久化（权威）：见 §3.3。
- 前端 sessionStorage 兜底：每次阶段保存乐观写入 `sessionStorage['conv_draft_' + projectId]`（非敏感、可丢失）；网络中断时 `useConversationSession` 优先读 sessionStorage 渲染，待网络恢复再与服务端对齐。详见状态管理实现.md §5。
