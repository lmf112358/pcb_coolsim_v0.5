## 概述

本文档在《系统架构设计 v1.0》§2 技术栈概览基础上，将每一项技术选型细化到「可执行决策级」：给出具体版本、选型理由、备选方案对比与已知风险，并逐一引用对应的 ADR 与 PRD 非功能需求（第 17 章）。

所有选型均复用既有架构决策，**不引入 PRD v0.5.1 已移除的「冷站配置 / Cooling Station Configuration / P&ID 生成 / 水蓄冷配置」相关实体或服务**（ADR-0005 已被 v0.5.1 取代，不在本文档规划范围内）。通用 HVAC 词（Chiller / 冷冻机 / cooling）仅作为领域物理名词出现。

## 1. 前端栈

| 类别 | 技术 | 版本 | 用途 |
|------|------|------|------|
| 框架 | React | 18.x | UI 组件库 |
| 语言 | TypeScript | 5.x | 类型安全 |
| 构建工具 | Vite | 5.x | Dev Server + 生产构建 |
| UI 库 | Ant Design | 5.x | 企业级组件库（表单/表格/树） |
| 服务端状态 | React Query | 5.x (@tanstack/react-query) | 服务端状态缓存/失效/重试 |
| 客户端状态 | React Context | 18.x 内置 | 主题/语言/用户态等轻量全局态 |
| 路由 | React Router | 6.x | 客户端路由 |
| 地图 | Leaflet | 1.9.x | 项目地理分布可视化 |
| 2D 画布 | Fabric.js | 6.x | 2D 平面图编辑器（模块三） |
| 图表 | ECharts | 5.x | 8760h 逐时数据可视化 |
| 国际化 | react-i18next | 14.x | 中英文切换（F9-019） |
| HTTP 客户端 | Axios | 1.x | API 通信 + JWT 拦截 |

### 1.2 选型理由、备选对比与风险

- **React 18 + TypeScript（决策：React）**
  - 理由：PRD NF-028 允许「Vue3 / React + TypeScript」，架构 §2.1 已定 React；React 生态对 Fabric.js / ECharts 集成成熟，社区与招聘面更广。
  - 备选 Vue3：能力与生态相当，但团队已沿 React 栈落地，双栈会增加维护成本，故不选。
  - 风险：React 18 Concurrent 特性在 10 万级节点树（NF-001）下需配合虚拟滚动，避免整树重渲染。
- **Vite 5（决策：Vite）**
  - 理由：冷启动 < 1s、HMR 快、产物体积优于 Webpack；TS/ESM 原生支持。
  - 备选 Webpack / CRA：配置重、构建慢，仅在遗留集成时考虑。
  - 风险：Fabric.js 6 为 ESM 大版本，需确认 Vite 依赖预构建无误。
- **Ant Design 5（决策：AntD）**
  - 理由：开箱即用的表单校验、树、表格、抽屉，契合国内后台审美与数据密集型界面。
  - 备选 MUI：偏 Material 风格，不符合既有设计规范。
- **React Query 5 + Context（决策：分层状态）**
  - 理由：服务端状态（房间/项目/计算结果）用 React Query 统一管理缓存与失效（对齐架构 §7.2 缓存策略）；仅主题/语言/当前用户等客户端态用 Context，职责清晰。
  - 备选 Redux Toolkit：适合复杂客户端状态，但服务端状态用 React Query 更省心、减少样板代码。
  - 风险：须严格区分两类状态，避免把服务端数据误存 Context 导致缓存失效。
- **Leaflet 1.9（决策：Leaflet）**
  - 理由：轻量、无商业 token 依赖，满足地图标点需求。
  - 备选 Mapbox / Google Maps：需密钥与计费，超出 v0.5 范围。
- **Fabric.js 6（决策：Fabric）**
  - 理由：成熟的对象模型画布，适合图元选择/拖拽/属性编辑（2D 编辑器）。
  - 备选 Konva：性能优秀但对象编辑链路需自研更多。
  - 风险：v6 为 ESM 重构版，迁移成本高于 v5。
- **ECharts 5（决策：ECharts）**
  - 理由：PRD 外部依赖 D8 指定；26280 点（8760h×3 年）逐时曲线渲染 < 3s（NF-007）靠其 Canvas 渲染与 dataZoom 胜任。
  - 备选 Recharts：React 友好但大数据量下性能不足。

引用：F2-001（四级树形导航 → React Query + 虚拟滚动）、NF-028（前端栈）。

## 2. 后端栈

### 2.1 选型清单（对齐架构 §2.2）

| 类别 | 技术 | 版本 | 用途 |
|------|------|------|------|
| Web 框架 | Django | 5.x | 主 Web 框架 |
| REST 框架 | Django REST Framework | 3.15.x | API 层 |
| 认证 | djangorestframework-simplejwt | 5.x | JWT（Access + Refresh） |
| 数据库 | PostgreSQL | 16.x | 主关系库 |
| 连接池 | pgbouncer | 1.22.x | 连接复用（应对并发，§7.3） |
| 缓存/Broker | Redis | 7.x | 缓存 + Celery broker/result |
| 异步任务 | Celery | 5.x | 异步任务队列 |
| 定时调度 | Celery beat | 5.x | 周期任务（气象拉取/每小时更新） |
| 实时通道 | Django Channels | 4.x | WebSocket 进度推送 |
| 时序扩展 | TimescaleDB | 2.x | PostgreSQL 扩展，8760h 时序数据 |
| 文件存储 | MinIO | latest | S3 兼容（PDF/Excel/气象上传） |
| 反向代理 | Nginx | 1.26.x stable | SSL 终止/静态/负载均衡 |

### 2.2 选型理由、备选对比与风险

- **Django 5 + DRF 3.15（决策：Django）**
  - 理由：PRD NF-029 允许「Python / Node.js」；选 Django 因 ORM 成熟、Admin 可复用、DRF 提供标准化序列化/权限/分页（架构 §5 API 结构），且与 Celery/Channels 同源生态。
  - 备选 FastAPI：异步原生、性能好，但权限/序列化/Admin 需自研，团队 Django 资产更厚。
  - 风险：Django 默认同步 WSGI，长任务（动态仿真/报告）必须卸载到 Celery（见 ADR-0002），不能用同步视图阻塞。
- **JWT 认证（simplejwt）（决策：JWT）**
  - 理由：Access 15min + Refresh 7d（架构 §6.1，NF-021）；无状态、契合 SPA 多端。
  - 备选 Session + Cookie：不利于前后端分离与多端，且需同源。
  - 风险：Refresh Token 泄露 → 用 HttpOnly + 短期 + 后端吊销表兜底；密码存储用 bcrypt（NF-020）。
- **PostgreSQL 16 + pgbouncer（决策：PG）**
  - 理由：JSONB 配置存储（§7.3）、窗口函数、成熟主从复制；连接池应对 1000+ 房间并发计算。
  - 备选 MySQL：JSONB/窗口函数与扩展生态弱；TimescaleDB 无对应方案。
  - 风险：pgbouncer transaction 模式下禁用 session 级特性（如 session 级 advisory lock、部分 Channels 用法），需最终确认部署模式（见待确认）。
- **Redis 7（决策：Redis）**
  - 理由：缓存 + Celery broker + result backend 三合一（ADR-0002）；实时预览 30s TTL 缓存（架构 §4.2）。
  - 风险：单点 → 用 AOF 持久化 + 监控（§6 风险缓解）。
- **Celery 5 + beat（决策：Celery）**
  - 理由：NF-032 与 ADR-0002 明确；异步仿真/报告/气象拉取/每小时更新。
  - 风险：队列积压 → Worker 水平扩缩（见部署架构 §8）。
- **Nginx（决策：Nginx）**
  - 理由：SSL 终止、静态资源、多副本 API 负载均衡、WebSocket 反代（§8.1/§8.2）。
- **TimescaleDB 2（决策：TimescaleDB）**
  - 理由：作为 PG 扩展存储 8760h 逐时数据，超表自动按时间分区，查询聚合高效（详见部署架构 §5）。
- **MinIO（决策：MinIO）**
  - 理由：S3 兼容、可自托管，存储生成的 PDF/Excel 与上传的气象 CSV/EPW（NF-025 限制类型/≤50MB）。

引用：F1-001（JWT 登录）、ADR-0002（Celery + Redis）、NF-030（PG + TimescaleDB）、NF-032（Celery + Redis）。

## 3. 计算引擎

### 3.1 选型清单（对齐架构 §2.3）

| 类别 | 技术 | 版本 | 用途 |
|------|------|------|------|
| 语言 | Python | 3.11+ | 核心语言（与后端同栈） |
| 焓湿计算 | psychrolib | latest | 焓值/湿球等（D3，精度 > 0.1%） |
| 数值计算 | NumPy | 1.26.x | 向量化 8760h 计算 |
| 数据处理 | Pandas | 2.x | 逐时数据框操作 |
| HTTP 客户端 | Requests | 2.x | 气象 API 拉取（D1 / D7） |

### 3.2 选型理由、备选对比与风险

- **Python 3.11 + (NumPy / Pandas / psychrolib)（决策：Python 向量化栈）**
  - 理由：PRD NF-031 指定 NumPy/Pandas 向量化、psychrolib 焓值；与 Django 同语言，计算服务可直接复用模型与系数表。
  - 备选 纯 Python 循环 / 自研焓湿公式：循环方式无法满足 < 30s（NF-006 / SAC-12）；自研焓湿公式易错且无交叉验证。
  - 风险：逐时仿真体量（8760h × 3 年 × 1000+ 功能区域）需向量化 + Celery 分片并行，单进程会超时。
- **比例系数法（决策：单一系数矩阵）**
  - 理由：ADR-0003 将原本两套系数表合并为 `coefficient_matrix` 单一权威矩阵，按 季节 / 小时 / 生产负荷率 将静态设计负荷转换为逐时负荷；系统默认值与项目级覆盖清晰、可审计。
  - 备选 双表 / 硬编码：维护负担与混淆（ADR-0003 已否决）。
- **精度要求（对齐验收）**
  - 静态冷量：与手工 Excel 验算偏差 < 0.1%（SAC-2，F4-001 土建冷量 Q_civil = civil_load_index × area / 1000 kW）。
  - 动态仿真（方式一，气象驱动）：与独立 Python 脚本偏差 < 1%（SAC-3，F6-001 获取最近连续 3 年逐时气象约 26280 条）。
  - 计算时间分辨率固定 1 小时（内部约束 C1），不计算分钟级瞬态。

引用：F4-001（静态冷量公式与精度）、F6-001（8760h 逐时气象与仿真）、ADR-0003（系数矩阵）、C1（1h 分辨率）、SAC-2 / SAC-3（验收精度）。

## 4. DevOps 与基础设施

### 4.1 选型

| 类别 | 技术 | 用途 |
|------|------|------|
| 容器化 | Docker | 应用与依赖封装（NF-027） |
| 单机编排 | docker-compose | 本地开发 / 单机生产起步（§8.1） |
| 编排（预留） | Kubernetes | 多副本横向扩展（NF-033，P1） |
| CI/CD | GitHub Actions | 构建/测试/镜像推送（§2.4） |
| 环境隔离 | dev / test / prod 三套 | 独立数据与环境变量（见部署架构 §2） |

### 4.2 选型理由、备选对比与风险

- **Docker + docker-compose（决策：Compose 起步）**
  - 理由：NF-027 明确要求 Docker + docker-compose 单机起步；compose 文件即部署契约，开发/测试/生产共用同一镜像。
  - 备选 裸机/虚拟机：环境漂移、不可复现。
- **Kubernetes（决策：P1 预留）**
  - 理由：NF-033 预留 K8s 扩展；满足 §7 Scalability 横向扩展、滚动更新与自愈。
  - 备选 纯 compose 多容器：无自动扩缩/自愈。
  - 风险：运维复杂度上升，是否在 v0.5.1 交付期落地待确认（见待确认）。
- **GitHub Actions（决策：GH Actions）**
  - 理由：仓库托管于 GitHub（§2.4），PR/推送触发 CI；构建镜像并推送至镜像仓库。
  - 备选 GitLab CI：仓库不在 GitLab，不采用。
- **环境隔离（决策：三套独立）**
  - 理由：dev/test/prod 使用独立 compose project 或 K8s namespace，配置经环境变量/Secret 注入，杜绝数据串扰与密钥泄露。

引用：NF-027（Docker + compose）、NF-033（K8s 预留）。
