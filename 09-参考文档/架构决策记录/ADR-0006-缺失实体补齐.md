# ADR-0006: 数据库设计缺失实体补齐（user / role / simulation_run / weather_data / ratio_coefficient + room.water_tier_id）

**Status:** Accepted
**Date:** 2026-07-13
**Decision Makers:** 架构师

---

## Context

在 `docs/prd-revision` 分支的 04 实现级 Spec 中，多处将以下实体标为「待确认」，原因是《数据库设计》（`01-系统级-Spec/数据库设计.md`）§4 未定义这些表，导致后端无法无歧义开工：

- **`user` / `role`**（账户与权限）：服务层设计.md、数据访问层设计.md 引用 accounts 模块的用户/角色/权限表，但 15 张表内未定义，项目级数据隔离依赖 `ProjectMember` 模型却无载体。
- **`room.water_tier_id` 字段缺失**：ADR-0001 与 API 总览 §6.2/§6.3 均引用 `room.water_tier_id`，但 §4.4 `room` 表未列出该字段，模块-04 SQL 已引用而 §4 缺失。
- **`simulation_run`**（仿真任务）：动态仿真/异步任务依赖 `simulation_result` / `simulation_summary` 两类结果落库表，但不在 15 张表内。
- **`weather_data`**（逐时气象）：动态仿真气象驱动依赖 8760h 逐时气象，但仅 `city_config` 存静态设计参数，逐时气象存储表未定义。
- **`ratio_coefficient`**（比例系数）：ADR-0003 与模块-06 引用比例系数表（动态仿真取负荷率=100% 列），但不在 15 张表内。

## Decision

正式将上述 5 类实体纳入《数据库设计》§4，并对 `room` 补列：

1. **新增 `user`**（§4.16）：用户账户，含 `username` / `password_hash` / `role_id`（FK→`role.id`）/ `email` / `is_active` / `last_login` / 时间戳。
2. **新增 `role`**（§4.17）：角色表，含 `name`（admin / pm / engineer / viewer，对应系统架构 §6.2 权限矩阵）/ `permissions`（JSON 权限矩阵）/ `description` / 时间戳。
3. **新增 `simulation_run`**（§4.18）：仿真任务表，含 `project_id`（FK）/ `mode`（weather_driven | ratio_coefficient）/ `status`（PENDING→STARTED→SUCCESS|FAILURE）/ `progress` / `result_summary` / `error_message` / 时间戳；对齐 §11 动态仿真与 Celery 异步（ADR-0002）。
4. **新增 `weather_data`**（§4.19）：逐时气象表，含 `city_id`（FK→`city_config.id`）/ `timestamp` / `dry_bulb_temp` / `wet_bulb_temp` / `humidity` / `atmospheric_pressure` / `source`；建议建为 TimescaleDB 超表，按 `(city_id, timestamp)` 分区。
5. **新增 `ratio_coefficient`**（§4.20）：比例系数表，含 `building_type` / `equipment_type` / `coefficient_value` / `applicable_scope` / `is_default` / `project_id`（FK，项目级覆盖）；对齐 ADR-0003「比例系数表统一」。
6. **`room` 补列 `water_tier_id`**（§4.4）：FK→`water_temperature_config.id`，[INPUT]，说明「冷冻水温度档位」，解决模块-04 SQL 已引用但 §4 缺失的问题。
7. **§3 表总览**：基础信息类 +`user`/`role`、配置类 +`ratio_coefficient`/`weather_data`、结果类 +`simulation_run`；总表计数 15 → **20**；§5 补主键/外键/业务索引。

**关于 8760h 逐时结果**：复用既有 `room_air_volume_result` 作为 TimescaleDB 超表（按 `room_id` + 时间 分区），**不另建表**；PRD §19 别名 `DynamicLoadHourly` / `room_hourly_load_result` 均指向该表。

## Rationale

1. **消除后端阻塞**：04 层所有「待确认」实体引用均获得权威定义，后端可据此建表、写迁移、实现仓储与序列化器。
2. **与既有决策一致**：`user`/`role` 对齐系统架构 §6.2 权限矩阵；`simulation_run` 对齐 ADR-0002（Celery 异步状态机）；`ratio_coefficient` 对齐 ADR-0003（比例系数表统一）；`room.water_tier_id` 落实 ADR-0001（末端负荷按水温档分配）。
3. **奥卡姆剃刀**：仅补齐 04 层实际引用且 §4 缺失的实体，未新增无关表（如导出任务文件元数据表未纳入本次范围，见下）。
4. **复用而非新建**：8760h 逐时明细复用已有 `room_air_volume_result` 超表，避免重复存储与口径分裂。

## Consequences

### Positive
- 后端可无歧义开工：按 §4 字段级定义建表与写迁移。
- 认证接口（03-接口级-Spec）依赖 `user` / `role` 完成 RBAC 与项目级数据隔离。
- 动态仿真（04 / 06）依赖 `simulation_run` + `weather_data` 完成异步任务编排与气象驱动计算。
- 比例系数法（PRD §10.3，ADR-0003）依赖 `ratio_coefficient` 查表取系数 k(t)。
- `room.water_tier_id` 补列后，模块-04 SQL 引用与 §4 定义一致。

### Negative
- `user` / `role` 的引入带来认证与权限实现成本（但属既有 §6.2 需求，非新增范围）。
- `weather_data` 逐时数据量较大（每城市约 26280~26304 条），需 TimescaleDB 超表与分区策略支撑。

### Risks
- 导出任务状态 / 文件元数据表（异步任务设计.md 待确认项 4）本次未纳入，仍列为待确认，需在后续 ADR 单独决策——本 ADR 仅闭环上述 5 类实体 + `room.water_tier_id`。

## Alternatives Considered

### Alternative 1：保持 15 张表，04 层自行定义这些表
**Rejected：** 04 层各自定义会造成口径分裂、命名不一致，且违背「系统级 Spec 为权威数据源」的约定，后端仍无法无歧义开工。

### Alternative 2：将 8760h 逐时结果另建 `DynamicLoadHourly` 表
**Rejected：** 与既有 `room_air_volume_result` 重复存储风量/负荷结果，且 PRD §19 已将其列为别名；复用超表更简洁，符合奥卡姆剃刀。

### Alternative 3：单独建 `permission` 表
**Rejected：** 权限以 JSON 存入 `role.permissions` 即可表达 §6.2 权限矩阵，无需独立 `permission` 实体，避免过度设计。
