# ADR-0003: Consolidate Coefficient Tables into Single Matrix

**Status:** Accepted (values pending calibration)
**Date:** 2026-07-09
**Decision Makers:** Domain Expert, Architect, PM

---

## Context

The dynamic simulation uses "coefficient tables" (比例系数表) to convert static design loads into hourly loads based on:
1. Time of day (hour)
2. Season (summer/winter/transition)
3. Production load rate (0-100%)

The original design had **two separate coefficient tables**:
- One for "weather-driven" simulation
- One for "coefficient method" simulation

This created confusion about which table to use and maintenance burden.

## Decision

**Consolidate into a single authoritative coefficient matrix table `RatioCoefficient`:**

```sql
CREATE TABLE RatioCoefficient (
    id SERIAL PRIMARY KEY,
    season VARCHAR(20),        -- summer, winter, transition
    hour INTEGER,              -- 0-23
    production_rate DECIMAL,   -- 0.0 to 1.0
    coefficient DECIMAL,       -- multiplier
    source VARCHAR(50),        -- 'default', 'project_override'
    project_id INTEGER,        -- NULL for system defaults
    UNIQUE(season, hour, production_rate, project_id)
);
```

**Usage Rules:**
- System provides default coefficients (industry standard)
- Projects can override specific coefficients
- Dynamic simulation (weather-driven) uses column where `production_rate = 1.0`
- Coefficient method uses all columns based on user-configured production rate

## Rationale

1. **Single Source of Truth:** One table eliminates confusion
2. **Flexibility:** Projects can customize coefficients
3. **Maintainability:** Easier to update and validate
4. **Traceability:** Clear audit trail of coefficient sources

## Consequences

### Positive
- Eliminates coefficient table confusion
- Supports project-level customization
- Clear data lineage

### Negative
- Need migration path if existing data uses old tables
- Coefficient values need domain expert calibration

### Risks
- Incorrect coefficients → Mitigated by validation and reference data

## Alternatives Considered

### Alternative 1: Keep Two Separate Tables
**Rejected:** Maintenance burden, confusion about which to use

### Alternative 2: Hard-code Coefficients
**Rejected:** Inflexible, requires code changes for updates
