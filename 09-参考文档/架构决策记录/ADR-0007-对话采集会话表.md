# ADR-0007: 对话式采集会话与消息表

**Status:** Accepted
**Date:** 2026-07-14
**Decision Makers:** 架构师、产品、后端负责人

---

## Context

PRD §6.10 对话式采集（Conversational Data Collection）是模块二「项目采集」的一条新增采集通道，提供如下能力，均依赖服务端持久化会话状态：

- **断点续采（F2-057）**：用户中途中断（关闭/刷新浏览器、网络抖动、主动保存退出）后，再次进入需从上一次进度继续，不能丢步。
- **对话历史回看（F2-051 / F2-058）**：用户在多步问答过程中需要回看先前回答，确认已填内容。
- **保存退出 / 跳过待补（F2-058）**：允许某一步暂不回答、标记为「待补」，后续继续推进或回填。
- **修改上一步（F2-047）**：允许回到上一轮问答修改已提交的答案。

PRD 附录 E 原列出的 22 张数据表（详见《数据库设计》§3 表总览）**未单列对话采集表**。若下游不落表、仅靠前端内存或 LocalStorage 暂存：

1. 刷新 / 重开浏览器后会话状态丢失，无法支撑断点续采（F2-057）。
2. 消息历史无法回看，无法支撑 F2-051 / F2-058。
3. 多端 / 多人协作场景下会话无法共享与恢复。

因此需要新增服务端持久化的「会话级」与「消息级」两张表。

## Decision

**新增两张表（表名 PascalCase，字段 snake_case），支撑对话式采集：**

### 1. `ConversationSession`（会话级）

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | PK | 会话主键 |
| `project_id` | FK → `Project.id` | 所属项目 |
| `current_stage` | ENUM | 当前所处采集阶段 s1~s6 |
| `stage_status` | JSON | 各阶段状态（未开始 / 进行中 / 已完成 / 待补） |
| `draft_payload` | JSON | 当前草稿载荷（尚未确认的暂存数据） |
| `created_at` | timestamp | 创建时间 |
| `updated_at` | timestamp | 最近更新时间 |

- 一个项目可有多次采集会话（如反复修改），最新一条作为当前活跃会话。
- `current_stage` 与 PRD §6.10 的六阶段（s1 项目基本信息 → … → s6 复核确认）对齐。

### 2. `ConversationMessage`（消息级）

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | PK | 消息主键 |
| `session_id` | FK → `ConversationSession.id` | 所属会话 |
| `role` | ENUM | `system` / `user` / `assistant` |
| `content` | TEXT | 消息正文 |
| `extracted_payload` | JSON | 本轮从用户回答中抽取的结构化数据 |
| `stage` | ENUM | 本消息所属阶段 s1~s6 |
| `timestamp` | timestamp | 消息时间戳 |

- `role` 区分系统提示、用户作答、助手追问 / 复述。
- `extracted_payload` 记录本轮抽取结果，用于回看与回填。

### 草稿暂存策略

- 房间草稿（对话中尚未确认的房间数据）用 `Room.status = draft` 暂存，确认后转为 `active`，避免另设房间草稿表。
- 已确认的结构化数据落回既有的项目 / 建筑 / 楼层 / 房间表，与表单式采集共用同一套领域模型，不重复存储。

## Rationale

1. **闭环 PRD 需求**：F2-057 断点续采、F2-051 / F2-058 历史回看、F2-058 跳过待补、F2-047 修改上一步，均需服务端持久化会话与消息，前端暂存无法满足。
2. **复用领域模型**：抽取确认后的数据仍落到既有领域表，房间草稿复用 `Room.status`，不污染主表语义。
3. **与既有决策一致**：会话表对齐 ADR-0006 的实体补齐思路（补齐 04 层引用而 §4 缺失的实体），不引入与采集无关的表。

## Consequences

### Positive
- 断点续采与历史回看能力具备，PRD §6.10（F2-046 ~ F2-061）可落地。
- 多端 / 多人协作下会话可共享与恢复。
- 草稿与正式数据分离（`Room.status = draft`），主表口径不被污染。

### Negative
- 表数 +2（突破 PRD 附录 E 原 22 张表的约定），需同步更新《数据库设计》§3 表总览与附录 E。
- `ConversationMessage` 会随使用持续增长，需定期归档策略（**v0.6 评估**：按项目归档 / 按时间冷热分离 / 软删除保留审计）。

### Risks
- 会话状态机（`current_stage` × `stage_status`）与房间草稿（`Room.status`）的一致性需在服务层保证，避免会话推进而草稿未落库的窗口期。

## Alternatives Considered

### Alternative 1：仅用前端 LocalStorage 暂存会话
**Rejected：** 无法支撑断点续采（刷新 / 换端即丢）与多端协作；不符合 F2-057 的服务端持久化要求。

### Alternative 2：复用 `SimulationRun` 或通用任务表承载会话状态
**Rejected：** `SimulationRun`（ADR-0006）是异步仿真任务状态机，语义与采集会话不同；强行复用会造成状态语义混淆与查询口径分裂。

### Alternative 3：会话与消息合并为单表
**Rejected：** 会话级（1 行 / 会话）与消息级（N 行 / 会话）语义不同，合并会导致字段稀疏与查询复杂；分离更清晰。
