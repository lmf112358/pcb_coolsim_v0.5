## Overview

This document details all user stories for PCB-CoolSim v0.5, with acceptance criteria, priority, and traceability to PRD requirements.


## Module 1: Account & Project Management

### US-1.1: Project Map Dashboard

**User Story:**
As an HVAC engineer,
I want to see all my projects on a map,
So that I can quickly locate and access projects.

**Acceptance Criteria:**
- [ ] Map displays all projects user has access to
- [ ] Projects shown as markers with status colors (blue=design, green=active)
- [ ] Clicking marker shows summary card (name, city, buildings, total load)
- [ ] Summary card has "Enter Project" button
- [ ] Map loads in < 3 seconds
- [ ] Search box filters projects by name

**Priority:** P0
**PRD Reference:** F1-009, F1-010, F1-011, F1-014
**Test Cases:** TC-1.3.1 through TC-1.3.4

---

### US-1.2: Project Creation

**User Story:**
As an HVAC engineer,
I want to create a new project with city selection,
So that the system automatically gets local weather data.

**Acceptance Criteria:**
- [ ] Project creation form has required fields: name, city, location
- [ ] City dropdown has ~300 Chinese cities
- [ ] Selecting city auto-fills outdoor design parameters
- [ ] System triggers async weather data fetch after creation
- [ ] Default water temperature configs created (7/12, 12/17)
- [ ] User notified when weather data is ready

**Priority:** P0
**PRD Reference:** F1-015 through F1-022
**Test Cases:** TC-1.2.1 through TC-1.2.5

---

### US-1.3: User Authentication

**User Story:**
As a user,
I want to login with my credentials,
So that I can access the system securely.

**Acceptance Criteria:**
- [ ] Login form with username and password
- [ ] Valid credentials return JWT access + refresh tokens
- [ ] Invalid credentials show error message
- [ ] Access token auto-refreshes before expiry
- [ ] Expired refresh token redirects to login
- [ ] Logout clears tokens

**Priority:** P0
**PRD Reference:** F1-001 through F1-006
**Test Cases:** TC-1.1.1 through TC-1.1.6

---

### US-1.4: Role-Based Access Control

**User Story:**
As a project manager,
I want to control who can access my project,
So that I can manage team permissions.

**Acceptance Criteria:**
- [ ] 4 roles: Admin, PM, Engineer, Viewer
- [ ] PM can invite users to their projects
- [ ] PM can assign roles (Engineer, Viewer)
- [ ] Engineers can edit data in assigned projects
- [ ] Viewers can only view data
- [ ] Users cannot access projects they're not invited to

**Priority:** P0
**PRD Reference:** F1-024 through F1-029
**Test Cases:** TC-1.1.1 through TC-1.1.6

### US-2.4: Conversational Data Collection (SOP Six-Stage)

**User Story:**
As an HVAC engineer,
I want to complete data collection through a guided dialogue,
So that I can capture process/load information consistently without manual form filling.

**Acceptance Criteria:**
- [ ] Entry from workbench "对话采集" button opens dialogue panel
- [ ] Six-stage SOP advances sequentially (展示确认 → 工艺设备 → 负荷特征 → 运行策略 → 约束条件 → 汇总确认)
- [ ] Stage ① is display-only confirm (project name / geo / weather pre-filled from map)
- [ ] Per-region submit / save persists immediately to conversation_session.draft_payload
- [ ] Structured output matches Tab1 / Excel field definitions

**Priority:** P0
**PRD Reference:** 模块-02 §3 对话式采集 / PRD §6.10
**Test Cases:** TC-2.4.1 through TC-2.4.5

---

### US-2.5: Resume & Draft Recovery

**User Story:**
As an HVAC engineer,
I want to resume an interrupted dialogue,
So that I don't lose collected data.

**Acceptance Criteria:**
- [ ] Resume restores current_stage from conversation_session
- [ ] Completed fields re-display (回显)
- [ ] Room draft status = draft until final submit → active
- [ ] Refresh / re-open recovers the draft

**Priority:** P0
**PRD Reference:** 模块-02 §3.3 断点续采
**Test Cases:** TC-2.5.1 through TC-2.5.3

---

### US-2.6: Channel Parity (Tab1 / Excel / Dialogue)

## Module 7: 8760h Visualization & Validation

### US-7.1: Hourly Load Curve Exploration
**User Story:**
As an HVAC engineer, I want to view the 8760h × 3-year hourly load curve with year/month/day aggregation filters, so that I can analyze seasonal and daily load patterns for equipment sizing.

**Acceptance Criteria:**
- Hourly curve renders ~26280 points in < 3s (NF-SAC-07)
- Year/month/day views switch correctly
- Aggregation (avg/max/min) works
- Static vs dynamic comparison displayed
- LTTB downsampling preserves waveform

**Priority:** P0
**PRD Ref:** F7-001~F7-016, SAC-11

### US-7.2: Basic Design Validation
**User Story:**
As an HVAC engineer, I want the system to validate installed cooling capacity against annual load duration curve, so that I can confirm equipment sizing adequacy and economy.

**Acceptance Criteria:**
- Load duration curve with capacity line rendered
- Adequacy check: annual peak ≤ installed capacity
- Economy check: flag if load ratio < 50% for > 90% of year
- Failures shown with red warning + suggestions (rule-based, PRD §9.3)

**Priority:** P0
**PRD Ref:** F7-022~F7-024, F7-026, SAC-15

## Module 4 (supplementary): Water-Temperature Classification

### US-4.3: Terminal Load Water-Temperature Tier Allocation (ADR-0001)
**User Story:**
As an HVAC engineer, I want each room terminal load allocated to its designated chilled-water temperature tier (default mid-temp, configurable to low-temp per room), so that low-temp and mid-temp loads are summarized separately and accurately.

**Acceptance Criteria:**
- Terminal load allocated by Room.terminal_water_temp_config_id (default mid-temp 12/17°C)
- Fresh air load allocated by fresh-air config (single-mode all to that tier; two-stage proportional split)
- Per-room per-tier records in RoomLoadByWaterTemp
- Deviation from manual Excel < 0.1% (SAC-2/SAC-9)

**Priority:** P0
**PRD Ref:** F4-020~F4-028, ADR-0001, SAC-9

## Module 10 (supplementary): Multi-Segment Rate & Version History

### US-10.2: Multi-Segment Production Rate
**User Story:**
As an HVAC engineer, I want to configure multi-segment production load rates (e.g., first 3 days 50%, next 4 days 80%), so that I can simulate different production plans.

**Acceptance Criteria:**
- Multiple segments, each with rate (10%~100%) + duration (hours)
- Validation: sum of durations = 168 hours
- Default: one segment 100% × 168h

**Priority:** P0
**PRD Ref:** F10-011~F10-013, SAC-26

### US-10.3: Forecast Version History
**User Story:**
As an HVAC engineer, I want to retain each forecast version and switch between them, so that I can compare predictions over time.

**Acceptance Criteria:**
- Each version complete 168-point, stored in ForecastHourlyResult with fetched_at
- Retention: last 7 days auto versions + all manual; older auto aggregated daily

**Priority:** P0
**PRD Ref:** F10-020, §14.7, SAC-26

## Definition of Done

A user story is **done** when:

- [ ] All acceptance criteria met
- [ ] Code reviewed and approved
- [ ] Unit tests written and passing
- [ ] Integration tests passing
- [ ] Documentation updated
- [ ] No critical/high defects
- [ ] Product owner accepted
- [ ] Deployed to staging
